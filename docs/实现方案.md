# AI 消化科医生临床助手 — 全流程文书管理实现方案（v0.5 评审稿）

> 版本：v0.5（评审稿，待医生审核后修订）
> 定位：单机个人使用的消化科临床辅助工具，覆盖患者从入院到出院的全部医疗文书辅助书写与诊疗计划建议
> 数据边界：数据不出自有设备（Mac + 自建服务器内网）
> 前端基底：[mckaywrigley/chatbot-ui](https://github.com/mckaywrigley/chatbot-ui)（MIT，fork 修改）

---

## 1. 项目概述与目标

为临床医生构建一个本地化的 AI 消化科助手：医生在 Mac 上录入或上传检验检查结果（PDF / 粘贴文本）与用药信息后，AI 依据这些资料：

1. **全流程文书辅助书写**：以「一次住院」为单元，从入院到出院，辅助完成入院记录、查房记录、术前讨论、术前小结、操作/手术记录、术后病程、出院小结、出院医嘱等**全部医疗文书**的草稿；
2. **每份文书可对话调整**：生成草稿后，医生可通过上传补充材料和多轮对话持续调整文书内容，修订历史可回退；
3. **文书参考此前全部资料**：生成第 N 份文书时，自动参考患者信息、此前全部检验/检查/用药、此前已确认的文书（近期全文 + 更早摘要）；
4. **遵循本院格式与文风**：医生可预先上传各类文书的空白模板和少量已脱敏真实病历示例，AI 生成时自动遵循；
5. **给出下一步诊疗建议**：结构化输出检查建议、治疗建议、用药调整方向、随访计划与风险提示；
6. **界面基于 chatbot-ui**：以成熟的 ChatGPT 风格聊天界面（Next.js + React + Tailwind + TypeScript，MIT）为基础改造，复用其聊天组件与设置体系。

所有 AI 输出均为「草稿」，由医生人工审核确认后方可落库与导出，AI 仅承担辅助角色。

## 2. 关键决策（已与医生确认）

| # | 决策项 | 结论 | 说明 |
|---|--------|------|------|
| 1 | 使用规模 | 单机单用户，无登录体系 | 仅医生本人使用，架构最简 |
| 2 | 数据入口 | 手动录入 + PDF 上传 | 不对接医院 LIS/EMR（通常封闭） |
| 3 | 界面形态 | 基于 chatbot-ui 改造（Next.js/React/TS，MIT fork） | 运行于 Mac，浏览器访问 localhost:3000；复用聊天组件，新增医疗工作区页面 |
| 4 | 推理位置 | 服务器（H20 单卡） | Mac 仅做界面与解析 |
| 5 | OCR 位置 | Mac 本地（macOS Vision，Python 小助手） | 中文识别质量高、离线、敏感原件不出 Mac；服务器 PaddleOCR 为备选 |
| 6 | 存储方式 | 文件夹 + JSON 文件（无数据库） | 数据目录置于服务器；备份=复制目录；仓储层抽象，未来可迁数据库 |
| 7 | 技术栈 | 前端 TS/Next.js + 后端 Python FastAPI | 提示词仍为 .md 文本文件，改提示词即改文本 |
| 8 | 文书管理 | 全流程 + 注册表驱动 | 以 visit 为单位按时间线管理；新增文书类型无需改代码 |
| 9 | 每份文书 | 材料挂载 + 对话修订 + 修订历史 | 多轮对话调整草稿，历史可回退 |
| 10 | 模板与示例 | 空白模板 + 脱敏真实病历 few-shot | 生成/修订时自动注入；可选 QLoRA 微调（Phase 3） |
| 11 | 数据完整性 | AI 对话只改文书草稿 | 检验/用药等结构化资料修正走资料库人工编辑，AI 不直接改数据 |

## 3. 总体架构

```
Mac（本地界面 + 解析）
  ┌──────────────────────────────────────────────┐
  │ chatbot-ui fork（Next.js，localhost:3000）     │
  │  聊天界面（流式 / Markdown / 提示词库）          │
  │  + 医疗工作区页面：患者与住院 / 资料库 /          │
  │    文书时间线（生成→对话修订→确认→导出）         │
  │    / 模板与示例管理 / 诊疗建议                   │
  │ Python 解析助手：pdfplumber(数字型)             │
  │   + macOS Vision OCR(扫描型) + 项目归一化 + 置信度│
  └───────────┬──────────────────┬────────────────┘
              │ HTTP /api/*（CORS）│ OpenAI 兼容（自由对话直连）
  ┌───────────┴──────────────────┴────────────────┐
  │ Server（数据 + 推理）                          │
  │  FastAPI：存储(文件夹) / 时间线组装 / 文书生成    │
  │    / 对话修订(SSE) / 诊疗计划(guided_json)      │
  │    / 导出 .docx / 模板与示例管理                │
  │  data/ 文件夹存储（JSON，无数据库）              │
  │  vLLM + DeepSeek-R1-Distill-Qwen-32B (H20)    │
  └──────────────────────────────────────────────┘
```

- 医疗功能（文书生成、对话修订、诊疗计划）统一走 FastAPI（负责组装上下文、guided_json、一致性校验、落盘）；普通自由对话（如解读检验、问诊答疑）直接用 chatbot-ui 自带 OpenAI 兼容客户端连 vLLM；
- 远程访问：Tailscale / SSH 隧道；可选 API Token。

## 4. chatbot-ui 集成与改造方案（v0.5 核心）

### 4.1 fork 与基线
- `git clone` chatbot-ui（main，2.0）→ 独立仓库 `web/`；MIT 许可，仅作基线、不跟随上游（上游维护放缓）；
- 环境：Node 18、npm；开发 `npm run dev`，生产 `npm run build && npm start`。

### 4.2 剔除 Supabase 依赖（主要改造）
- 移除 supabase-js 调用、`supabase/` 迁移文件与 `supabase start` 步骤；
- 新增 `lib/api.ts` 统一 API 客户端（fetch → FastAPI），数据层接口与 chatbot-ui 原有数据流一一对应：会话、消息、文件夹、提示词、文件；
- 会话/消息默认落盘到 `data/chats/`（visit 维度），实现与 chatbot-ui 数据结构兼容的存储适配。

### 4.3 复用与保留
- 聊天组件：消息列表、输入框、流式 SSE 渲染、Markdown / 代码高亮；
- 设置页：模型提供商配置（预设 vLLM 的 OpenAI 兼容端点 `http://<server>:8000/v1`）、模型选择（32B / 14B）；
- 提示词库（sidebar Prompts）：保留，可作常用医嘱/文书片段快捷插入；
- 文件夹 / 搜索：保留，用于按患者/住院组织会话。

### 4.4 新增医疗工作区（核心开发工作）
- 侧边栏增加「患者与住院」选择器（患者 / visit 切换，贯穿所有页面）；
- **资料库页**：检验/检查/用药/材料列表（时间线排序），上传入口（调 Mac 解析助手）、修正、删除；
- **文书时间线页**：左侧文书列表（类型 + 状态徽章 + 摘要），右侧工作区：选择类型 → 生成（FastAPI）→ 聊天修订（复用聊天组件，SSE 流式）→ 修订历史浏览 / 回退 → 确认 → 导出 .docx；
- **模板与示例管理页**：上传 / 预览空白模板与脱敏示例、自动脱敏工具、脱敏复核、启用 / 停用；
- **诊疗建议页**：结构化计划卡片（guided_json 结果渲染），逐条采纳 / 忽略。

### 4.5 聊天 ↔ 文书绑定
- 文书工作区内的对话 = 该文书（document）的修订会话，消息经 FastAPI `document_chats` 落盘，每次修订写 `revisions/r{n}.md`；
- 自由对话 = 普通会话，落盘于 visit 聊天目录，与文书分离。

## 5. 硬件约束与模型选型

### 5.1 硬件事实
- NVIDIA H20 单卡：96GB HBM3、约 4TB/s 带宽，适合 LLM 推理，但**单卡装不下大模型**；
- 服务器 24 核 CPU、128GB 内存：足够承载后端、数据库与 vLLM 预填充卸载。

### 5.2 模型选型结论

| 模型 | 权重规模 | 单卡 H20 可行性 | 用途 |
|------|----------|----------------|------|
| DeepSeek-R1 / V3（完整版 671B MoE） | 4bit 量化仍需 ~335GB | ❌ 远超 96GB 显存 + 128GB 内存 | 排除 |
| **DeepSeek-R1-Distill-Qwen-32B（主模型）** | FP16 约 64GB | ✅ 剩余 ~30GB 做 KV cache，`max-model-len=32768` | 文书生成 + 诊疗计划 |
| DeepSeek-R1-Distill-Qwen-14B（备选） | FP16 约 28GB | ✅ 富余 | 起草速度翻倍，环境变量一键切换 |

- 均为 DeepSeek 官方蒸馏版（MIT 协议），中文与推理能力满足消化科结构化任务；
- 权重国内下载：ModelScope 或 hf-mirror.com（32B FP16 约 70GB）；
- 预期性能：H20 上 32B 解码约 50–80 tok/s；R1 系思考 token 较多，单份文书 30–90s（可接受）。

## 6. 文件夹存储设计（无数据库）

数据根目录 `data/`，目录结构即数据模型，每类数据为 JSON / Markdown 文件：

```
data/
├── registry/
│   └── document_types.json        # 文书类型注册表（阶段/顺序/模板引用/所需要素）
├── templates/                     # 全局资产：每类文书一个子目录
│   ├── admission/{template.md, examples/ex1.md, ex2.md}
│   ├── preop_discussion/…
│   └── …（与注册表一一对应）
├── chats/{visit_id}/              # 自由对话会话（chatbot-ui 兼容结构）
└── patients/
    └── {patient_id}/
        ├── patient.json           # 脱敏编号、性别、年龄、体重、过敏史、既往史、家族史
        └── visits/
            └── {visit_id}/        # 一次住院 = 全流程单元
                ├── visit.json     # 住院号、日期、状态、主诉、现病史、体查、诊断
                ├── labs/          # 检验结果，按日期命名 json（归一化项目/结果/单位/参考范围/异常标志/置信度）
                ├── imaging/       # 检查结果 json
                ├── endoscopy/     # 内镜结果 json
                ├── meds/          # 用药 json（药品/剂量/频次/起止/状态）
                ├── materials/     # 上传材料原件（pdf/图片）+ 解析结果 json + 置信度
                ├── documents/
                │   └── {doc_id}/  # 每份文书一个目录
                │       ├── doc.json      # 类型/日期/状态[草稿,已确认]/摘要/prompt版本
                │       ├── content.md    # 当前全文（Markdown）
                │       ├── revisions/    # 修订历史：r1.md、r2.md…
                │       └── chat.json     # 该文书的对话线程（role/内容/关联材料/revision）
                └── suggestions/   # 诊疗计划 json（类型/内容/采纳状态）
```

- **存储层抽象**：`backend/storage.py` 提供与数据模型一一对应的仓储接口（按患者/住院读写、按日期取时间线、取已确认文书与摘要、模板示例读取等），上层组装器 / 生成 / 对话引擎只依赖该接口，**不感知存储实现**；
- **原子写入**：写文件先写临时文件再 rename，断电 / 中断不产生半截文件；JSON 读取时校验，损坏则跳过并告警；
- **单用户低并发**：不做复杂锁，写操作以文件粒度原子替换；
- **备份**：整目录复制即备份；可选用 git 跟踪 `data/` 获得文书修订历史的免费版本管理（Phase 2）；
- **直读浏览**：可选 SMB / Syncthing 将该目录从 Mac 直接挂载浏览，不影响后端单写方；
- **未来迁移**：若数据量增长需查询能力，因仓储接口抽象，可平滑迁回 SQLite / PostgreSQL。

## 7. 文书类型注册表（全流程覆盖）

`registry/document_types.json` 登记全部文书类型，按阶段排序；**新增文书类型 = 注册表加一项 + 放模板/示例目录，无需改代码**：

| 阶段 | 文书类型（MVP 覆盖） | 生成时主要参考 |
|------|---------------------|----------------|
| 入院 | 入院记录、首次病程记录 | 患者信息 + 入院时检验/检查 + 主诉现病史 |
| 日常 | 日常病程记录、查房记录、阶段小结、交接班记录、会诊记录 | 时间线累计 + 当日新资料 |
| 术前 | 术前讨论记录、术前小结 | 全部资料 + 术前检查 + 拟手术方案 |
| 术中/操作 | 手术记录、操作记录（内镜/穿刺/ERCP 等） | 术前文书 + 术中记录素材 |
| 术后 | 术后首次病程、术后病程 | 手术/操作记录 + 术后检验 |
| 出院 | 出院小结、出院医嘱 | 全程资料 + 出院诊断 + 带药方案 |

每类文书配置：所需要素、提示词模板文件、是否需医生补充字段（如术前讨论需拟手术方案、操作记录需术者/麻醉方式）。

知情同意类文书**不纳入 AI 生成**（法律文书性质），仅可生成「谈话要点」草稿素材（可选）。

## 8. 模板与示例库（核心机制）

每类文书在 `data/templates/{code}/` 下可配置两项资产，生成与修订时由组装器自动注入：

1. **空白模板（本院格式）**：`template.md`，含各章节小标题、固定措辞、留空位，作为模型输出的**格式骨架**；
2. **少量真实病历示例（已脱敏）**：`examples/`，每类 2–5 份真实完成病历（脱敏后），作为 **few-shot 示例**，指导模型学习本院文风、详略程度与段落组织。

### 8.1 脱敏要求
- 示例入库前必须脱敏（姓名/身份证/手机号/住院号等替换为占位符）；
- 模板与示例管理页提供**自动脱敏辅助工具**（正则识别常见敏感字段）+ 强制人工复核，**未脱敏示例禁止启用**。

### 8.2 注入策略
- 生成上下文 = 格式模板 + 示例（按 token 预算选最近 1–3 份，超长截断）+ 实时时间线资料；
- 对话修订同样注入格式模板，保证修订后格式不漂移；
- 示例与模板为全局资产，所有患者文书生成时生效。

### 8.3 可选增强（Phase 3）
若 few-shot 仍不够，可对 32B 模型做 **QLoRA 微调**（用脱敏示例集），部署为第二个模型实例，路由切换，不影响主流程。

## 9. 软件设计（后端）

### 9.1 时间线上下文组装器（v3：累计全量 + 模板示例）

生成第 N 份文书时的上下文：

```
【格式模板】该文书类型空白模板
【示例】已脱敏真实病历 1–3 份（few-shot，预算内）
【患者资料】患者固定信息 + 住院要素（主诉/现病史/体查/诊断）
【时间线累计】检验（异常优先，限最近N条）+ 检查 + 用药（当前/历史）
【此前文书】最近 M 篇已确认文书全文 + 更早篇用其摘要
【本文书材料】挂载的新上传材料 + 医生本次补充要素（如拟手术方案）
```

- **Token 预算策略**：各块设上限，超限丢最旧非关键项并标注「更早资料未纳入，可补充」；
- **摘要机制**：每份文书确认时由模型产出 2–3 句摘要存入 doc.json，长期住院靠摘要控制上下文膨胀；
- **日期过滤**：组装按文书日期过滤（≤ 文书日期），支持补录错序文书。

### 9.2 文书生成引擎
- `POST /api/documents/generate`：选类型 → 组装上下文（含模板+示例）→ vLLM 生成草稿 → 写 revisions/r1.md；
- 采样：起草 temperature 0.3 / top_p 0.9，max_tokens 4096；
- 生成后一致性校验：输出中的检验数值/药名须能在输入中溯源，否则标黄提示。

### 9.3 对话修订引擎（每份文书一个会话）
- `POST /api/documents/{id}/chat`（SSE 流式）：医生发自然语言指令（改段落/补信息/换措辞/基于新上传材料更新）；
- 上下文 = 格式模板 + 当前文书全文 + 本会话最近 K 轮 + 新挂载材料 + 轻量时间线；
- 专用提示词 `chat_refine.md`：「只按指令修订，未涉及部分原样保留，输出修订后完整文书全文」；
- 每次回复 = 新 revision；UI 支持查看修订历史、一键回退；
- **约束**：对话只改文书草稿；若医生纠正检验数值等，系统提示「请到资料库修正」，保证数据-文书分层。

### 9.4 诊疗计划
- `POST /api/suggestions/plan`：guided_json 输出 `{检查建议[], 治疗建议[], 用药调整[], 随访计划[], 风险与注意[], 资料缺口[]}`，后端校验失败自动重试一次；渲染为结构化卡片，逐条采纳/忽略。

### 9.5 导出
- `POST /api/export/{doc_id}`：python-docx 生成中文 Word（宋体显式设置）。

### 9.6 提示词模板（prompts/）
按文书类型分文件：system_base / admission / progress_ward / stage_summary / handover / consultation / preop_discussion / preop_summary / op_record / procedure_record / postop_progress / discharge_summary / discharge_orders / labs_review / care_plan / chat_refine。

**硬性规则**：
1. 仅使用「【资料】」部分提供的信息，禁止虚构任何检验数值、药品名称、诊断或病史；资料中不存在的项目明确写「资料未提供」；
2. 文书按给定格式模板输出，语言精炼、符合国内医疗文书规范；
3. 涉及用药时只给出调整方向与需要监测的指标，不给出具体剂量，注明「具体剂量请结合药品说明书与患者肝肾功能由医生确定」；
4. 若检验结果提示肝肾功能异常（ALT/AST 升高、eGFR 下降），在用药建议中提示相应监测或调整方向；
5. 对话修订时未涉及的部分原样保留；
6. 输出仅是草稿，最终由医生审核确认。

**采样参数**：文书起草 temperature 0.3 / top_p 0.9；诊疗建议 0.4；max_tokens 4096；重试时 temperature 0。

### 9.7 推理服务（vLLM）
- 镜像 `vllm/vllm-openai`，参数：`--model deepseek-ai/DeepSeek-R1-Distill-Qwen-32B --gpu-memory-utilization 0.90 --max-model-len 32768 --served-model-name gi-assistant`；
- NVIDIA Container Toolkit，驱动 ≥ 550、CUDA 12.x（H20 为 sm_90，vLLM 官方支持）；
- 启用 guided_json（XGrammar/Outlines）保证诊疗计划输出可解析；
- 14B 备选模型通过环境变量切换，无需改代码。

## 10. 端到端全流程数据流

```
入院：建患者+住院 → 传首份检验/材料（Mac 解析）→ 生成入院记录（模板+示例+资料）→ 对话修订 → 确认
住院中：每日传新检验 → 生成查房病程（参考此前全部）→ 对话修订 → 确认
术前：补术前检查 → 生成术前讨论/术前小结 → 确认
操作/术后：操作/手术记录 → 术后病程 → 确认
出院：出院小结/出院医嘱（参考全程）→ 确认 → 导出 .docx
```

每份文书确认后自动进入后续文书的时间线上下文；模板与示例全局生效；AI 对话仅作用于文书草稿。

## 11. 部署方案

### 11.1 Mac（前端 + 解析）
- Node 18 + npm 安装 chatbot-ui fork：`npm install && npm run dev`（端口 3000）；
- Python 3.11 + `install_mac.sh`（pdfplumber / pyobjc / ocrmac / openai / httpx）提供解析助手；Vision OCR 免额外下载模型；
- 自由对话：chatbot-ui 设置页预设 vLLM 端点，无需额外配置。

### 11.2 服务器
- `docker-compose.yml`：`inference`（vLLM，`--gpus all`）+ `backend`（FastAPI）两服务；
- 卷挂载：`/models`（权重）、`./data`（数据目录，JSON 文件，无数据库）；
- 备选：systemd + venv 非容器部署说明。

### 11.3 直读浏览与备份
- 可选 SMB 共享或 Syncthing 同步 data/ 目录，Mac Finder 直接查看；
- 备份 = 复制 data/ 目录；中文 README 含两端启动、换模型、远程访问、备份、模板/示例导入说明。

## 12. 安全与合规

1. 数据全链路不出自有设备：扫描件原件仅存 Mac，结构化数据存服务器，均不出内网；
2. 患者以脱敏编号记录（建议不存真实姓名/身份证号）；
3. 所有 AI 输出为「草稿」，医生是最终审核人与责任主体；
4. 界面常驻「辅助工具、非诊断依据」提示；
5. 示例病历必须脱敏后方可启用（自动脱敏工具 + 人工复核）；
6. 本地操作日志（生成/修改记录），单机场景从简。

## 14. 验收标准（可测量）

1. 前端以 chatbot-ui fork 运行于 Mac（localhost:3000），**无 Supabase 依赖**，可独立启动；
2. 同一患者从入院到出院全流程走通：入院记录 → 查房病程 → 术前讨论/小结 → 操作/手术记录 → 术后病程 → 出院小结/医嘱，各类型文书均能生成；
3. 生成文书**遵循上传的本院空白模板格式**（章节结构一致），与示例病历**文风一致**，且与时间线资料一致、无虚构；
4. 文书工作区内聊天修订：连续 5 轮修改指令均正确落实，且未涉及段落保持原样（diff 可核），修订历史可回退；
5. 自由对话可直接连 vLLM 解答（如检验解读），会话与文书分离存储；
6. 资料库上传 PDF / 粘贴，Mac 本地解析（数字文本 + Vision OCR）入库存证；
7. 示例库仅启用已脱敏示例（未脱敏不可启用），自动脱敏工具 + 人工复核流程可用；
8. 文书日期过滤正确（补录不引用未来资料）；新文书类型通过注册表添加无需改代码；材料可挂载到具体文书并参与生成/修订；
9. 诊疗计划返回结构化卡片（检查/治疗/用药调整/随访/风险）；
10. 单份文书生成 ≤ 90s；草稿可编辑、导出 .docx；数据全部为文件夹 + JSON 可读形式：复制 data/ 即完整备份，断电/中断不产生半截文件，重启数据不丢。

## 15. 失败模式与对策

| 失败模式 | 对策 |
|----------|------|
| chatbot-ui 对 Supabase 深度耦合 | 数据层集中替换为 lib/api.ts，先跑通会话读写再扩展 |
| 上下文超长（模板+示例+时间线） | 示例预算 1–3 份、摘要机制、块预算截断、标注未纳入项 |
| 示例未脱敏泄露 | 未脱敏示例禁止启用 + 自动脱敏工具 + 人工复核 |
| 对话修订漂移（改坏未涉及内容） | chat_refine 提示词约束 + 修订前后 diff 展示 + 可回退 |
| 模型虚构数值/药名 | prompt 硬性规则 + 生成后一致性校验标黄 |
| 文书日期错序补录 | 组装按文书日期过滤 |
| 文件写入中断 / JSON 损坏 | 临时文件 + rename 原子写；读取时校验，跳过损坏项并告警 |
| JSON 输出非法 | guided_json + 自动重试一次（temperature 0） |
| 显存 OOM | 调低 gpu-memory-utilization 或切换 14B 模型 |
| 中文乱码 | 全链路 UTF-8 + docx 显式设置中文字体 |
| Node 版本不兼容 | 固定 Node 18（chatbot-ui README 要求） |

## 16. 待评审问题（供医生审核时确认）

1. **chatbot-ui 运行位置**：Mac 本地运行（推荐，匹配「本地界面」且 OCR 就近）vs 服务器运行、Mac 纯浏览器（此时 OCR 需改服务器端 PaddleOCR 或 Mac 解析助手上传文本）；
2. **保留 chatbot-ui 现有功能**：文件夹/搜索、提示词库、模型切换等是否全部保留（建议保留，零成本）？
3. **自由对话功能**：是否需要直接连 vLLM 的普通问答（如检验解读）？（建议保留）
4. **文书类型集合**：MVP 文书类型（第 7 节）是否符合贵科实际？需增删哪些（如转科记录、抢救记录、输血记录）？
5. **模板复杂度**：空白模板以 Markdown/文本为主是否可行？本院模板是否含复杂表格（需评估渲染与生成难度）？
6. **示例数量**：每类文书示例预期多少份（2–5 份够否）？可否提供 2–3 类文书各 1 份脱敏示例供开发阶段校准？
7. **对话与资料边界**：对话调整除改文书外，是否需要 AI 直接修资料库（当前设计不允许，保证数据完整性）？
8. **结构化字段**：手术/操作记录的术者、麻醉方式等字段是否表单预填后再生成？
9. **知情同意**：只做「谈话要点」草稿是否可接受？
